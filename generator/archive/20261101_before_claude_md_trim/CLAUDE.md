## 1. プロジェクトの概要

「モンじゃん!」は、2027年1月初旬にイオンモールで行う展示用のゲームです。
子供(小学生がメイン)が選んだ**動物**と、スマホで撮った**身の回りの物**をAIで合体させて、オリジナルのモンスターを作ります。

最終的なゲームでは、じゃんけんバトルやカード印刷まで行いますが、**今回作るのは中身の仕組みを確かめるためのプロトタイプだけ**です。

### 今回のプロトタイプの目的

「写真 + 動物」から、OpenAI APIでモンスター情報と画像を作れるかを確かめる。
あわせて、次の3点を計測・確認する。

- 処理時間(撮影から画像ができるまで)
- 画質(子供向けのかわいい絵柄になるか)
- 判定の精度(物を正しく認識できるか)

## 2. 今回の範囲

### 作るもの
- スマホで撮った写真をPCに送る仕組み(PCのボタンをきっかけに、スマホで撮影する)
- 写真に写っている物をAIで判定し、モンスター情報を作る処理
- 写真とモンスター情報から、モンスター画像を生成する処理
- 結果をPCの画面に表示し、フォルダに保存する処理

### 作らないもの
- タイトル画面などのゲーム画面
- じゃんけんバトル
- カードの生成・印刷
- 見た目の作り込み(確認用のシンプルな画面で十分)
  - ※ 2026年10月31日:依頼者の希望で、PC用・スマホ用の画面をゲームっぽい見た目にした(`static/style.css`)。
    検証用の情報(判定のJSON・時間・料金・名前のテスト)は、PC画面の「開発者メニュー」にまとめてある。
    それまでの画面は `archive/20261031_before_game_ui/` に控えてある
  - ※ 同日、PC画面を展示の大画面向けに作り直した(下の「6-1. PC用ページ」)。

## 3. 使う技術

- **言語**:Python 3.11以上
- **サーバー**:FastAPI + Uvicorn
- **リアルタイム通信**:WebSocket(FastAPIの標準機能)
- **画面**:HTML + CSS + 素のJavaScript(フレームワークは使わない)
- **演出のライブラリ**(2026年11月1日。依頼者の指定で、まず fantasy テーマでためす)
  - GSAP 3.15.0(SplitText も):誕生の流れ・名前が1文字ずつ跳ねる。全プラグイン無料・商用可(Webflow の標準ライセンス)
  - tsParticles 4.5.0(bundle 版):ひびからもれる光の粒・葉っぱの紙吹雪。MIT
  - **ネットから読まず `static/vendor/` に置いている**(モールの Wi-Fi が不安定でも動くように)。版を上げるときは置きかえる
  - tsParticles 4 は書き方が 3 と違う(色は `particles.paint.color`。`particles.color` では白になる)
  - Howler.js 2.2.4:効果音(`static/common/sound.js` の `window.sfx.play(名前)`。全テーマ)。**今の音は Python で合成した仮の音**。
    素材が決まったら `static/sounds/` の同じ名前のファイルを置きかえる(`static/sounds/README.md`)。`?sound=0` で鳴らさない
- **フォントも手元に置いている**(`static/vendor/fonts/`。Google Fonts から保存。どれも SIL OFL 1.1)。各ページは `<ページ名>.css` を読む。
  ネットを止めた状態で、全ページの字体が出ることを確認済み(2026年11月1日)
- **テスト**:pytest(`python -m pytest`)。`tests/conftest.py` が、からうちモードにしたうえで API を呼ぼうとしたら失敗させるので、**料金0円**。
  写真と結果は一時フォルダに保存する(`uploads/`・`outputs/` を汚さない)
- **画像処理**:Pillow
- **AI**:OpenAI公式のPythonライブラリ(`openai`)
- **設定管理**:python-dotenv(`.env`ファイル)

## 4. システム構成

```
[スマホ(ブラウザ)]  ←WebSocket / HTTP→  [ノートPC:FastAPIサーバー]  ←HTTPS→  [OpenAI API]
                                              ↑
                                    [PC画面(ブラウザ)]
```

- ノートPCでサーバーを動かし、PCのブラウザとスマホのブラウザの両方からアクセスする
- PCとスマホは**同じWi-Fi**につなぐ
- スマホにアプリのインストールは不要(ブラウザだけで動く)

### 6-1. PC用ページ(`/`)

**2026年10月31日:展示の大画面(1920×1080)向けに作り直した。** デザインは案A「ひみつけんきゅうじょの がったいマシン」。
それまでの画面は `archive/20261031_before_lab_ui/` に控えてある。

**同日、見た目をテーマごとに切りかえられる作りにした**(依頼者の指定。今後いくつかのデザインを試すため)。
それまでの `static/pc.html` / `pc.js` / `style.css` は `archive/20261031_before_themes/` に控えてある。

- 動き(撮影・生成・場面の進行・開発者メニュー)は共通の `static/common/app.js`、見た目はテーマごとに `static/themes/<名前>/`
- `/?theme=lab` のように切りかえる。何も付けないときは `.env` の `PC_THEME`(既定 `lab`)。知らない名前なら既定のテーマ
- テーマの一覧は `GET /api/themes`(`static/themes/` の中で `index.html` があるフォルダ。表示名は `theme.json`)。開発者メニューからも切りかえられる
- 今あるテーマ:`lab`(ひみつけんきゅうじょ)/ `fantasy`(モンスターのたまご:ひびが増えて、割れて生まれる)/
  `cardpack`(カードパック かいふう:パックのふちが光り、破れてカードが出る)/ `pot`(まほうの おなべ:泡と湯気が増え、ふたが飛んで生まれる)/
  `gacha`(ガチャガチャ:ハンドルが回り、転がり出たカプセルが割れて生まれる)/ `summon`(しょうかんの まほうじん:輪が順に光り、光の柱から召喚される)。
  2026年11月1日に cardpack・pot、続けて gacha・summon を足した
- **新しいテーマは、フォルダを足すだけで選べる**。`index.html` に用意する要素(ID)は `app.js` の先頭の「テーマとの約束」を参照
- 進み具合は、`app.js` が `#stage` に付ける `--progress`(0〜1)と `data-level`(0〜5)を、テーマが CSS で見せ方に変える
  (lab:液体とメーター、fantasy:ひびの伸び具合(16本が --progress で少しずつ伸びる)、cardpack:光るふちの数、pot:泡・湯気・火の大きさ、gacha:ハンドルの角度とメーター、summon:光る輪の数)。テーマ側で JavaScript を書かなくてよい
  - 段階ごとの見た目は opacity・stroke などの**静的な指定**で出し、transition やアニメーションで出さない。
    回る・ゆれる要素の中では、途中の状態のまま止まって見えた(fantasy のひび、summon の輪、gacha のメーター)
- 場面転換は `#stage` に付く `shut` の class をテーマが CSS で見せる(lab:鉄のシャッター、fantasy:葉っぱの群れ、cardpack:扇形に広がるカード、pot:湯気、gacha:降ってくるカプセル、summon:広がる魔法陣)。
  閉じる・開く時間は、テーマの CSS 変数 `--scene-close-ms` / `--scene-open-ms` で変えられる
- **テーマは JavaScript で演出を足してもよい**(2026年11月1日。なくても動く)
  - `window.themeFx.birth(showCard)` を用意すると、誕生の演出をまかせられる。「ため」のあと `showCard()` で s4 にし、終わったら Promise を終える。
    失敗しても `app.js` がかならずカードを出す

### 6-2. スマホ用ページ(`/phone`)

子供が触る想定なので、文字は大きく、ボタンは押しやすくしてください。

**動物を選ぶのはスマホ側です。**PCでは選びません。

- **待機中**:「PCの ボタンを まってね」と表示
- **撮影待ち**(PCから合図が来たとき):次の2つを表示する
  - **動物の選択**:プルダウンで5種類から選ぶ(最初から1つ選ばれている状態にする)
  - 大きな「とる!」ボタン
- **送信中**:「おくっているよ…」と表示
- **送信完了**:「おくったよ!」と表示し、数秒後に待機中に戻る
- **できあがり**(2026年11月1日に追加。ためし):生成が終わると、モンスターの名前と絵を表示する。
  あとで、しっかり作ったカードとして表示する予定。絵を見せているあいだは待機中に戻さず、次に PC で「スマホでとる」が押されたら撮影の画面になる

写真と、選んだ動物は**一緒に**サーバーへ送ります。

カメラの起動には、次の書き方を使ってください。

```html
<input type="file" accept="image/*" capture="environment">
```

- `getUserMedia()`は使わない(HTTPSが必要になるため)
- ブラウザの制約上、カメラを開くにはスマホ上でのタップが必要。PCのボタンだけで撮影まで完結させようとしないこと

## 7. 処理の流れ

1. PCで「スマホでとる」を押す
2. サーバーがWebSocketでスマホに「撮影して」と合図を送る
3. スマホに**動物のプルダウン**と「とる!」ボタンが出る
4. 子供が動物を選び、「とる!」をタップ → カメラで撮影
5. スマホ側で、写真を**長辺1024pxのJPEG**に変換し、**選んだ動物と一緒に**サーバーに送る(canvasで変換。容量を減らすのと、iPhoneのHEIC形式への対策)
6. サーバーが写真を受け取り、Pillowで開けるか確認する。動物の名前は`photo_id`と紐づけて覚えておく
7. サーバーがWebSocketでPCに「写真が届いた」と知らせ、PCに写真と動物の名前を表示する
8. PCで「生成する」を押す
9. **判定**:写真と動物をテキスト用モデルに渡し、モンスター情報をJSONで受け取る
10. **チェック**:返ってきた内容を確認し、不正な値はデフォルト値で補う
11. 撮り直しが必要と判定された場合は、その理由をPCに表示して終了する
12. **画像生成**:写真と、テンプレートに当てはめたプロンプトを画像生成モデルに渡す
13. **保存**:結果をフォルダに保存する
14. PCの画面に結果を表示する

## 8. WebSocketのメッセージ

接続先:`/ws?role=pc` または `/ws?role=phone`

メッセージはJSONでやりとりします。

| 送る方向 | type | 内容 |
|---|---|---|
| サーバー → スマホ | `capture_request` | 撮影してほしい |
| サーバー → PC | `photo_received` | 写真が届いた(`photo_id`、画像のURL、スマホで選ばれた`animal`を含める) |
| サーバー → PC | `phone_status` | スマホの接続状態(`connected: true/false`) |
| サーバー → スマホ | `upload_done` | 受け取り完了 |
| サーバー → PC・スマホ | `progress` | 生成の進み具合(`stage`:`naming` / `drawing` / `done` / `retake` / `error`)。ローディングの表示に使う。`drawing` には名前の候補 `name_choices` と、画像生成の目安の秒数 `expected_seconds` を含める。`done` には、できたモンスターの絵のURL `image_url` を含める |
| サーバー → PC | `name_chosen` | 子供がスマホで名前を選んだ(`photo_id`、`name`)。カードの名前を書きかえる |

写真の送信そのものは、WebSocketではなくHTTPのPOSTで行います。

## 9. APIのエンドポイント

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/` | PC用ページ |
| GET | `/phone` | スマホ用ページ |
| WS | `/ws` | WebSocket |
| POST | `/api/capture-request` | PCの「スマホでとる」ボタン。スマホに合図を送る |
| POST | `/api/upload` | スマホから**写真と動物**(`photo`と`animal`)を受け取る |
| POST | `/api/generate` | 判定と画像生成を実行する(`photo_id`を受け取る。動物は`photo_id`に紐づけて覚えてあるものを使う) |
| GET | `/outputs/...` | 生成結果の画像を表示する |
| POST | `/api/choose-name` | 子供がスマホで選んだ名前(`photo_id`と`name`)を受け取る。候補にない名前は断る。画像ができたあとなら `result.json` も書きかえる |
| POST | `/api/name-test` | 名前のテスト(`animal`・`object_name`・`count`)。写真も画像生成も使わず、名前だけを作る |

## 10. 物の判定(テキスト用モデル)

### 使うモデル
- `.env`の`TEXT_MODEL`で指定する
- 第一候補は**GPT-6 Luna**(OpenAIで一番安いモデル)
- **画像の入力に対応しているかを公式ドキュメントで確認すること**。対応していなければGPT-6.1 Solを使う

**確認済み(2026年10月28日)**

| 項目 | 結果 |
|---|---|
| モデルID | `gpt-6-luna` |
| 画像入力 | **対応している**(入力は text, image) |
| 構造化出力 | **対応している**(`structured_outputs`) |
| 呼び出し方 | Responses API の `client.responses.parse(text_format=...)` |
| 実測の所要時間 | 約4〜7秒(当初)。融合デザインなどを足したあとは約8〜16秒 |

そのため、GPT-6.1 Solへの切り替えは不要。

### 返してもらうJSON

```json
{
  "needs_retake": false,
  "retake_reason": "",
  "object_name": "はさみ",
  "element": "とがってる",
  "monster_name": "ハサミオン",
  "description": "するどい たてがみで なんでも きりさく ゆうかんな モンスター"
}
```

- 決まった形式で受け取るため、OpenAI APIの構造化出力(JSONスキーマ指定)の機能を使うこと

#### モンスター名(2026年10月31日に作り直した)

**名前は子供がスマホで選ぶ**:判定が終わる(画像生成が始まる)と、スマホに「きみの モンスターの なまえは〇〇だ!」と
「この なまえに する! / ほかに さがす」を出す。候補は判定で作った3つ(チェックに合格したもの)を順番に見せるだけで、
作り直しはしない(待ち時間も料金も増やさないため)。画像ができてから20秒選ばなければ、出ている名前に決める。

名前は子供が最初に目にする「当たり外れ」なので、しっかり組んだ(`prompts.NAME_RULES`)。

- 単語を2つ並べるだけにせず、音を混ぜて1つの言葉にする。何の動物か・何の物か、少なくとも片方は分かるようにする
- カタカナだけ・3〜8文字・言いやすいリズム。にごった音や「ン」「ー」で強そうな響きにする
- 悪口・下品・こわすぎる言葉、実在のキャラクターや商品の名前、言いにくい名前は使わない
- **候補を3つ(それぞれ違う作り方で)作らせ、プログラムがチェックに合格したものからランダムに1つ選ぶ**。
  それまでは同じ組み合わせだと同じ名前になりやすかった(ティラノサウルス×はさみは5回中3回が「ハサミラノ」)
- 物を取り込む場所(あご・しっぽなど)も伝えるが、部位の言葉(テイル・ヨロイなど)は名前に入れない
- 例は仕様の「ライオン × ドライヤー → ドライオン」だけにした(テストで使う「はさみ」の例は、写されるので外した)
- **2026年11月1日:名前のつけ方を作り直した**(それまでの版は `archive/20261101_before_name_rules/`)
  - 実際の名前の多くが「頭を2文字ずつ切ってつなげただけ」(タカサミ・ゴリバサミ・ウサケイ)で、
    「かいじゅうの おもちゃ」の飾りことばまで使っていた(カイネコ)
  - 考える手順を書いた:材料の音を集める → 重なる音を探す → 強い響きに整える → 声に出して確かめる。
    物は英語や動き・音の言葉に言いかえてよい(はさみ → シザー・チョキ)。物の飾りことば(おもちゃの・〜だい)は使わない
  - 3つの作り方を1つずつ使う:A 重ね合わせ / B 言いかえ合体 / C 怪獣ネーム(両方の音をまぜてから強い語尾)。
    良い順に並べさせ、プログラムは 50% / 30% / 20% の重みで選ぶ(`validator.NAME_PICK_WEIGHTS`)
  - 試したこと(名前のテスト。6組×3回を4回、合計 約7円):
    - 3つ目を「特徴ネーム」(部位の言葉を足す)にしたら、ライハサテイル・テプヨロイザメのように長くなった → 部位の言葉を禁止
    - 「語尾をつける」だけだと、ハサミドン・ウサギドンのように片方だけになった → 両方の音をまぜてから、と書いた
  - 良くなった例:シザレオン / シザホーク / タカッター / ラビクロック / シャーカッター / ペタシャーク
  - 残っている課題:ゴリラ×えんぴつはゴリペン・ゴリピツが続く。3つ目が「〜ガ」をつけただけになりやすい
- **PC画面の「7. 名前のテスト」で、写真も画像生成も使わずに名前だけを何回か作れる**(1回 0.1円以下)。
  判定と同じ「名前のつけ方」とチェックを使う。結果は `outputs/name_tests.jsonl` に残る(からうちモードのときは残さない)

### AIへの指示に含める内容
- 写真に写っている物の名前を、子供にわかる言葉で答える
- 性質は、次の6つから**必ず1つ**選ぶ
  - あつい / みず / でんき / かたい / とがってる / やわらかい
- モンスター名は、動物と物の名前を組み合わせたカタカナの名前(例:ライオン×ドライヤー → ドライオン)
- 説明文は、子供向けにひらがな中心で書く
- 次の場合は`needs_retake`を`true`にし、理由を書く
  - 人(顔・体)が写っている
  - 物がはっきり写っていない
  - 子供に見せるのにふさわしくない物が写っている

### チェックのルール(`validator.py`)

| 項目 | ルール | 不正なときの扱い |
|---|---|---|
| `element` | 6種類のどれか | 「かたい」にする |
| `monster_name` | 10文字以内 | 10文字で切る。空なら「なぞのモンスター」 |
| `name_candidates` | カタカナだけ・2〜10文字・NGの言葉なし・小さい文字が続かない・物と動物の名前を並べただけでない | 合格した候補からランダムに1つを `monster_name` にする |
| `description` | 40文字以内 | 40文字で切る |
| `object_name` | 空でない | 「なにかのもの」にする |
| JSON全体 | 形式が正しい | すべてデフォルト値にする |

## 11. 画像生成(画像生成モデル)

### 使うモデル
- `.env`の`IMAGE_MODEL`と`IMAGE_QUALITY`で指定する
- 候補は**GPT Image 2**と**GPT Image 1 Mini**。どちらも試せるようにする
- GPT Image 1.5は提供終了予定の情報があるので使わない
- **撮った写真を入力として渡す**ため、画像の編集・参照に対応した呼び出し方を使うこと
- モデル名やパラメーター名は新しいものなので、**必ずOpenAIの公式ドキュメントで確認してから書くこと**

**確認済み(2026年10月28日)**

| 項目 | 結果 |
|---|---|
| モデルID | `gpt-image-2`(既定スナップショット `gpt-image-2-2026-04-21`) |
| 呼び出し方 | `client.images.edit(model=..., image=..., prompt=..., size=..., output_format=..., n=1)` |
| 写真の渡し方 | `image=("photo.jpg", 画像のバイト列, "image/jpeg")` |
| 戻り値 | `response.data[0].b64_json`(base64。URLでは返らない) |
| 画質 | `IMAGE_QUALITY=medium` で**実際に動くことを確認済み** |
| 実測の所要時間 | 約35秒(1024×1024 / medium) |

- 画質については公式ドキュメント内で記述が食い違っている
  (APIリファレンス:「`gpt-image-2` では `quality` を省略する」/
   画像生成ガイド:「以前のGPT Imageモデルは `high` までの画質に対応」)。
  実際には `medium` を送って正常に生成できた。
  念のため`generator.py`では、画質が原因で断られた場合だけ画質を外して1回やり直す作りにしている
- `gpt-image-1-mini` も `.env` の `IMAGE_MODEL` を変えるだけで試せる
- **2026年10月30日:`IMAGE_MODEL` を `gpt-image-2.5-sunburst` に切り替えた**(依頼者の指定)
  - 公式の位置づけ:Sunburst は「画像の生成と編集でいちばん高性能」。画像生成ガイドは「編集の正確さが最も重要なら Sunburst」としている
  - `gpt-image-2.5-flare` は「高品質な画像をいちばん速く」。待ち時間が問題になったら候補
  - `chatgpt-image-latest` は**非推奨(Deprecated)**なので使わない
  - 2.5 系も `images.edit` で写真を渡せる。1024×768 と画質 `medium` はそのまま使える(画質は `xhigh` / `max` も追加された)
  - トークンあたりの単価は `gpt-image-2` と同じだが、1枚あたりのトークン数は違う可能性がある。実際の料金は `result.json` の `usage` で確認する
  - 元に戻すときは `IMAGE_MODEL=gpt-image-2` にする

### 出力
- サイズ:**1024×768(4:3 横長)**。`.env`の`IMAGE_SIZE`で変えられる
  - カードの絵柄の枠と、ゲーム内で使う画像の両方に使う想定
  - APIの決まりで、幅・高さとも**16の倍数**、縦横比は**1:3〜3:1**の範囲にする
  - 正方形(1024×1024)より画素が少ないので、料金も安くなる
- 形式:PNG

| 差し込む値 | `{animal}`(動物)、`{object_name}`(物)、**融合デザインの4項目** |
| 画風 | 透明感のある水彩ゲームイラスト風。**かわいさ60% / かっこよさ40%** |

#### 融合デザイン(`design_plan`)

**2026年10月30日:画像プロンプトを、依頼者の指定した「ChatGPTが考えたプロンプト」に差し替えた。**
それまでの作り(Ver.1.1復帰版 + 置き換え対応表 + `FUSION_MODE`)は `archive/20261030_before_chatgpt_prompt/` に控えてある。

画像プロンプトの差し込み口に合わせて、判定(テキスト用モデル)の構造化出力 `design_plan` を次の6項目にした。

| 項目 | 内容 |
|---|---|
| `animal_identity` | 動物の特徴(顔つき・骨格・手足としっぽの数・足先の形) |
| `primary_fusion` | メインの融合(物のいちばん目立つ特徴を、体のどの部位にどう変形して取り込むか。1か所) |
| `secondary_fusion` | サブの融合(2番目の特徴を、別の部位に控えめに。1か所) |
| `ability` | 能力(体にパーツを足さず、攻撃エフェクトとして描けるもの) |
| `pose` | ポーズ(やや低い視点で映える躍動的な構え) |
| `background` | 背景(動物のすみか × 物の使われ方を組み合わせた幻想的な景色) |

- 各項目は `validator.py` で**120文字以内**に切り、空なら既定値で補う
- 画像プロンプトの「動物:{animal_identity}」は、動物名が抜けないように「ライオン(たてがみのある…)」の形で差し込む
- 組み合わせごとの判断は判定モデルに任せ、画像プロンプトには共通の原則だけを書いている
- **同日、画像プロンプトをシンプルな形(約570字)に作り直した**。直前の詳しい版は `archive/20261030_before_simple_prompt/` に控えてある
  - 依頼者の指定した基本:動物と写真を合成する / かっこよさ70%・かわいさ30% / 写真を最大限に生かす / 武器として合成してもよい / 背景はモンスターに合ったもの
  - 具体的な指示は、判定の `design_plan` を【このモンスターの設計図】として差し込む形で渡す
    (設計図なしのシンプル版では、物がまるごと体の前に重ねて描かれた)
  - 「物をまるごとの形で、体の前に重ねて置かない」を1行入れている
  - 画風は「セミリアルなアニメ調、ハイファンタジー系ゲームのモンスターイラスト、厚塗り風の繊細な陰影、重厚な金属質感、シネマティックなライティング、壮大で迫力のある構図」(2026年10月30日に依頼者の指定で変更。
    それまでは「太く強弱のある輪郭線、セル塗り、強いハイライトとコントラストの2Dイラスト」)
  - プロンプトを比べるときは、1枚ずつではなく決まった組み合わせ(例:ライオン×はさみ、ゾウ×はさみ、形の違う物)で試す
  - **融合の型を毎回ランダムに選ぶ**(武器 / 体の部位 / よろい)。「必殺技」の型は、物の形をエフェクトで
    描くことになり、向きが逆になるなどの崩れが目立ったので外した。判定モデルにまかせると、同じ物に
    いつも同じ設計を返し(はさみ → 前足の刃)、個性が出なかったため。`.env` の `FUSION_TYPE` で固定もできる
  - 判定の指示文に具体例を書くと、判定モデルがそのまま写す(2回起きた)。例は書き方の型だけにする
  - 物の形・色は残すが、素材や質感はファンタジーらしく変えてよい(本物の製品そっくりにしない)
  - サブの融合は、メインと離れた部位にする(同じ手足に集まると、物が体を貫いているように見える)
  - 必殺技のエフェクトは、物そのものの形にしない(はさみ形の光の向きが逆になった)。物の機能や動きを表す形にする
  - **演出(ポーズ・視点・表情・時間帯と天気)も毎回ランダムに選ぶ**(`prompts.STAGING_OPTIONS`)。
    判定モデルにまかせると、ポーズは毎回「前足を踏み出して吠える」、背景は8枚中8枚が「夕日のサバンナ」になった。
    AIのランダム性は絵の細部には効くが、「何を描くか」の大きな選択には効きにくい
  - 方針:**大きな方向だけをパターンで決め、中身(体の角度・しぐさ・景色の細部)はAIにまかせる**。
    動物や型に合わない組み合わせは、判定が近いものに変えてよい。候補は短い言葉にし、結果を見て足し引きする
  - 選ばれた型と演出は `result.json` の `monster.design_plan.fusion_type` / `staging` に残る
  - 武器型は、物まるごと(持ち手やネジまで含めた製品の形)を武器にしない。パーツを1つだけ選んで作り変える。
    はさみはもともと刃物なので、「武器にする」と言うと本物のはさみをそのまま描き、胸を貫く・指穴に前足を通す、などが起きた
  - 1つのパーツは体の1か所にしか使わない(持ち手が頭と手首の2か所に出て、はさみが2本あるように見えた)
  - 同じ融合の型は2回続けて選ばない。視点の候補から「斜め後ろから」は外した(胸や前足が見えず、体のつながりが崩れた)
- **短い画像プロンプト(`IMAGE_PROMPT_STYLE=simple`)を追加した**(2026年10月30日)
  - 依頼者が OpenAI 公式サイトの Playground で、写真を添付して短いプロンプトで生成したところ、アプリより良い絵になった。
    写真を添付しても良かったので、差の原因は写真ではなくプロンプト(「写真の物に忠実に」という指示の重なり)と考えられる
  - Playground の原文に「モンスター1体の全身」「文字・ロゴ・数字を入れない」だけを足している
  - simple では、判定の設計図・融合の型・演出は画像プロンプトに使わない(判定では作り、result.json に残す)
  - `detailed`(設計図つき)と `.env` で切り替えて比べる。どちらで作ったかは `settings.image_prompt_style` に残る
  - 短いプロンプトだけだと、取り込む場所が毎回ありがちな所になった(ティラノサウルス・サメ・ワニは毎回あご)。
    そこで「{物}の特徴は、主に「{場所}」に取り入れて」の1行だけを足し、場所は動物ごとの一覧からランダムに選ぶ
    (`prompts.FUSION_PARTS` / `ANIMAL_FUSION_PARTS`)。体のつくりに合わない場所は動物ごとに外している。
    同じ場所は2回続けて選ばない。`.env` の `FUSION_PART` で固定できる
  - 腕武器型とシルエット型は崩れやすい心配がある。シルエット型は、試して安全と分かるまで一覧に入れていない
  - ポーズ・視点・表情も1行で足す(`STAGING_OPTIONS` からランダム)。短いプロンプトだけだと似た構えが続いたため。
    時間帯・天気は入れない(背景は画像モデルにまかせる)
  - **説明文と画像の食い違いを直した**(2026年10月31日)。simple でも判定に「融合の型」と「演出の時間帯・天気」を伝えていたが、
    画像には伝えていなかったため、説明文に「よろいをまとい、ゆきの夜に ほえる」と書かれるのに、絵がちがった。
    simple では、判定にも**画像と同じ内容(取り込む場所・ポーズ)だけ**を伝え、説明文に天気・時間帯・場所や、
    取り込む場所以外の見た目を書かないよう指示している(`prompts.build_recognize_prompt_simple`)。
    simple では融合の型は選ばない(`design_plan.fusion_type` も入らない)
- **人の判定を直した**(2026年10月30日):物を手に持って撮ると、指が写っただけで `has_person=true` になり、
  人モードでは画像プロンプトに「この人を物の代わりに融合させる」が入って、はさみの写真なのに人の特徴が描かれた。
  「物を持つ手や指だけが写っているときは、人が写っているとみなさない」と判定に伝えている(撮り直しの判定も同じ基準)
- 性質(`element`)は画像プロンプトでは使わない(判定では出し、バトル用に保存する)
- 判定に考えさせる項目が増えると、判定の時間が伸びる(過去に30秒を超えてタイムアウトした)。
  タイムアウトは60秒にしているが、判定の時間はPC画面で確認すること

#### 以前の方針(参考として残す)

当初は次の内容を英語で書く方針だった。

- かわいい子供向けのモンスターのイラスト
- {動物}と{物}が合体したモンスター

## 14. エラー処理

- APIの呼び出しにはタイムアウトを設定する
  - 判定(テキスト用モデル):**60秒**(`API_TIMEOUT_SECONDS`)
    - ※ 当初は30秒。判定の指示を足すにつれて時間が伸び(約4〜7秒 → 約8〜16秒)、
      30秒を超えてタイムアウトしたので、2026年10月29日に60秒に上げた
  - 画像生成:**120秒**(`IMAGE_TIMEOUT_SECONDS`)
  - ※ 画像生成は30秒では間に合わない(gpt-image-2 / 画質medium / 1024×1024 で**実測 約35秒**)。
    そのため画像生成だけ別のタイムアウトにしている
- 失敗した場合は、エラーの内容をPCの画面に表示する(何が起きたかがわかるように)
- 画像生成がコンテンツフィルターで止められた場合は、同じ入力でリトライしない
- エラーが起きても、サーバー自体は止まらないようにする
- 本番では「失敗したら用意しておいた画像を使う」予定だが、プロトタイプでは**エラーをそのまま表示する**だけでよい(何が起きたかを確認するため)

## 16. サーバーの起動とネットワーク

- サーバーは`0.0.0.0`で起動し、同じネットワークのスマホからアクセスできるようにする
- 起動したときに、**スマホで開くURL(PCのLAN内IPアドレス)をターミナルに表示**する
- 起動したときに、**PC用ページをキオスクモード(全画面・アドレスバーなし)で開く**(2026年11月1日。依頼者の指定。`app/kiosk.py`)
  - Edge(なければ Chrome)を `--kiosk` 付きで立ち上げる。キオスク専用のプロフィールを使う(ふだんの Edge が開いていると全画面にならないため)
  - `python -m app.main` で起動したときだけ開く(`uvicorn` を直接動かす確認用の一時サーバーでは開かない)。`.env` の `KIOSK_MODE=false` で開かない
  - 終わるときは Alt + F4
- READMEに以下を書く
  - インストールと起動の手順
  - Windowsで初回起動時にファイアウォールの許可が必要なこと
  - PCとスマホを同じWi-Fiにつなぐ必要があること(公共のWi-Fiは端末同士の通信が禁止されていることが多い)

## 16-2. APIの料金の扱い

**APIの呼び出しには実費がかかります。無駄な呼び出しをしないでください。**

1回の生成(判定 + 画像1枚)は **$0.0498(約7.5円)** で、**ほぼ全額が画像生成**です
(2026年10月28日の実測。`gpt-image-2` / medium / 1024×768)。

- **画像生成を伴うテストを実行する前に、必ず依頼者に確認すること**
- 確認のときは「何回呼ぶか」「いくらかかるか」を先に伝えること
- APIを使わずに確かめられることは、次のどちらかで確かめる
  - **からうちモード**(`.env`の`DRY_RUN=true`):APIを一切呼ばず、ダミーの結果を返す。料金0円
  - 偽の返答(モック)に差し替えたテスト
- 同じ確認のために、同じ画像生成を何度も呼ばない
- 生成するたびに、実際のトークン数と料金の試算を記録する
  - PC画面の「APIの使用量と料金(試算)」
  - `outputs/.../result.json` の `usage`
- 単価は`app/pricing.py`に定義する(2026年10月28日時点の値。**使う前に公式ページで確認し直すこと**)

| 処理 | モデル | 1回あたり |
|---|---|---|
| 判定 | `gpt-6-luna` | 約 $0.0003(約0.1円) |
| 画像生成 | `gpt-image-2` / medium / 1024x768 | 約 $0.0495(約7.4円) |
| 画像生成 | `gpt-image-1-mini` | 約 $0.015(約2.2円) |

撮り直しと判定された場合は、画像生成を呼ばずに終了するので料金は判定の分だけで済みます。

## 17. 守ってほしいルール

- **APIキーをコードに直接書かない**。必ず`.env`から読み込む
- **画像生成を伴うテストの前に、依頼者に確認する**(1回あたり約7.5円かかるため)
- `.env`と`outputs/`は`.gitignore`に入れる
- コードのコメントは日本語で書く
- OpenAI APIの書き方は、推測で書かずに公式ドキュメントで確認する
- 仕様にない大きな変更をするときは、作業の前に確認する
- 一度に全部を作らず、次の順番で、動作を確認しながら進める
  1. FastAPIのサーバーとPC用・スマホ用のページを表示する
  2. WebSocketでPCとスマホをつなぐ(「スマホでとる」→スマホに「とる!」が出る)
  3. スマホからPCに写真を送る
  4. 物の判定(テキスト用モデル)
  5. 画像生成
  6. 結果の保存と時間の計測
